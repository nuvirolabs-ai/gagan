# Retailer catalogue performance probe, 2026-09-27

This is a **single-source diagnostic**, not a before/after fix comparison or a UX-02 PASS. Device: connected Moto E13 `ZD2229Q3KB`, Retailer `1.0.26`/code 26, Mahesh Store, hosted 52-group catalogue, Android font scale `1.3`, gesture navigation mode `2`. App data and account session were not cleared. The previously rejected `6f61e8bd` FlatList tuning is not in this build.

1. Force-stopped only the Retailer process and launched it to Home. Once Home loaded, reset `dumpsys gfxinfo` counters and tapped Products. The settled first catalogue screen showed **52 items** and usable cards. First-mount counters: 38 frames, 19 missed deadlines (50.0%), p95 61 ms, zero slow bitmap uploads; GPU image texture cache was about 42.3 MB. [First mount](retailer-v26-products-first-mount.png).
2. Reset counters on the loaded Products screen and performed eight same-direction 350 ms swipes. Counters: 262 frames, 12 missed deadlines (4.58%), p95 22 ms, zero slow bitmap uploads; GPU image texture cache was about 47.6 MB. The settled lower rows were rendered, not blank. [After eight swipes](retailer-v26-products-warm-eight-swipes.png). Process TOTAL PSS after scrolling was about 207,044 KB; there is no paired pre-scroll memory sample in this run.
3. A separate authenticated synthetic-retailer `GET /catalog` from the Mac returned 52 groups and 113 variants in about 703 ms. Among the first 12 unique image URLs in API order, five PNG HEAD responses were roughly 1.88-2.23 MB each; six JPEGs were roughly 82-93 KB, and one PNG was about 160 KB. These are transfer sizes, not decoded memory sizes or proof that those exact images were on screen during the measured frames. The synthetic OTP account hit its rate limit on the next request, so the full 52-image size distribution was not collected. No retry bypass was attempted.

The first-mount versus already-warm scroll difference and large PNG sample make image fetch/decode/cache a plausible hypothesis. They do **not** isolate JS render, UI thread, image decoding, network, API latency on the phone, or navigation remount cost. `ProductGroupCard` renders one `ProductThumb` per row with React Native `Image`, and `CatalogScreen` reloads and replaces its list on focus; both are candidates for controlled profiling, not proven root causes. A valid fix still needs equivalent cold/warm conditions, an unchanged account/catalogue/font/navigation setup, complete scroll/search/detail/Add regression, and memory/blank-cell checks. No FlatList tuning, asset rewrite, APK build, or hosted product change was made by this probe.
